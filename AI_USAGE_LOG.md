# AI Usage Log — The Interview Agent

This log documents how AI tools were used throughout development, for
Stage 1 (Eligibility) and Stage 2 (Authenticity Review). Entries are
added incrementally as the project progresses — this is not a
retroactive summary.

**Team:** Team [Hacksgirls]
**Project:** AI Interview Agent
**Primary AI tools used:** Claude (Anthropic) for architecture, code
generation, and debugging support. Gemini API (`gemini-2.5-flash`) as
the interview agent's own reasoning engine (this is a core dependency
of the product itself, not just a dev tool).

---

## Phase 1 — Problem Selection & Architecture

**Prompt (paraphrased):** Asked Claude to evaluate three provided
hackathon problem statements (ABTalks redesign, Interview Agent,
Autonomous AI Creator) against feasibility, technical depth, and
authenticity-review risk, and recommend one.

**Output used:** Selected "The Interview Agent" based on Claude's
comparative analysis. Used Claude's suggested high-level architecture
(planner → conversation state machine → session memory → feedback
generator) as the starting design.

**Human decision:** We reviewed the three options ourselves and agreed
with the recommendation before committing to it.

---

## Phase 2 — Data Modeling

**Prompt (paraphrased):** Provided the real `curriculum.json`,
`candidates.json`, and `technical-spec.md` files and asked Claude to
design Pydantic models matching the spec's request/response contract
exactly, and a `Candidate` schema matching the real data shape.

**Output used:** `app/models.py` — generated by Claude, verified by
us against the actual uploaded JSON files (confirmed it parses real
candidate records without errors).

**Human decision:** We chose to make `candidate` and `message` both
optional on the request model (since the spec's single endpoint
serves two different purposes) rather than create two separate
endpoints.

---

## Phase 3 — Interview Planner Logic

**Prompt (paraphrased):** Asked Claude to design the scoring logic for
which curriculum days to probe, based on a candidate's real mission
history (failed / skipped / high-attempt / first-try data).

**Output used:** `app/planner.py` — the scoring function and topic
selection logic. Verified against two real candidates (Sarah Johnson,
Isabella Rossi) to confirm the plans genuinely differ based on their
actual mission data.

**Human decision:** We reviewed and approved the scoring priority
(failed > skipped > struggled-but-passed > easy-pass) as reflecting
how a real interviewer would prioritize topics.

## Phase 4 — Gemini Integration

**Prompt (paraphrased):** Asked Claude to write the Gemini API wrapper
for question generation, follow-up decisions, and feedback synthesis,
using structured JSON output.

**Output used:** `app/llm.py`. Initially built against the
`google-generativeai` package; migrated to `google-genai` after
hitting a deprecation warning (Claude searched current documentation
to confirm correct migration syntax).

**Debugging (real, iterative):** Encountered an `API_KEY_INVALID`
error on first live test — resolved by generating a fresh key from
Google AI Studio. This was a genuine debugging step during
development, not a scripted demo.

**Human decision:** We wrote our own actual interview prompts /
system persona wording based on Claude's draft.

---

## Phase 5 — Session State & Interview Engine

**Prompt (paraphrased):** Asked Claude to design a state machine
guaranteeing the spec's minimum of 8 questions across 4+ curriculum
days, since the planner alone doesn't guarantee question count.

**Output used:** `app/session_store.py` and `app/interview_engine.py`
— the per-topic quota mechanism (`required_per_topic = ceil(8 /
num_topics)`) that forces additional questions only when genuinely
under quota, prioritizing Gemini's real follow-up judgment first.

**Verification (real, not simulated):** Ran the full state machine
with mocked LLM responses to confirm the 8-question/4-day minimum is
met before wiring in real API calls, to avoid burning API quota on
debugging.

## Phase 6 — API Endpoint

**Prompt (paraphrased):** Asked Claude to wire the engine into a
FastAPI app exposing exactly `POST /api/interview` per the spec, with
correct branching between "start" (candidate present) and "continue"
(message present) requests.

**Output used:** `app/main.py`. Tested with FastAPI's TestClient
(mocked LLM calls) to confirm the full request/response contract
matches `technical-spec.md`, then tested again with the real running
server and real HTTP requests.

## Phase 7 — Provider Migration: Gemini to Groq

**Issue encountered (real, live debugging):** Gemini's free tier
enforced a very low daily request quota (20 requests/day on this
project) that was exhausted mid-testing, causing every question,
follow-up, and feedback call to silently fail into fallback text.

**Decision:** Migrated the LLM wrapper (app/llm.py) from Google's
Gemini API to Groq (llama-3.3-70b-versatile), which offers a
significantly higher free-tier request budget suitable for
hackathon-speed iteration, while keeping identical function
signatures so no other module needed to change.

**Verification:** Ran a full 18-turn interview end-to-end post
migration, confirming real generated questions, contextual
follow-ups, and non-inflated structured feedback.

## Phase 7 — Frontend Chat UI

**Prompt (paraphrased):** Asked Claude for complete step-by-step
frontend guidance to create a chat interface for the interview agent,
including full code, files, and setup instructions.

**Output used:** `frontend/index.html` — a single-file HTML/CSS/JS
chat interface with a candidate dropdown (populated from
candidates.json), chat bubbles for the conversation, and a feedback
card rendered on interview completion. No frontend framework used —
kept intentionally simple to avoid build tooling overhead during the
hackathon window.

**Debugging (real, iterative):**
- First local test (opening the file directly via `file://`) failed
  silently on the candidate dropdown due to browser fetch restrictions
  on local files — fixed by serving the folder with
  `python -m http.server` instead of double-clicking the HTML file.
- "Start Interview" failed with `Failed to fetch` — root caused to
  the backend not yet having CORS enabled for cross-origin requests
  from the frontend's origin.

**Human decision:** Chose plain HTML/JS over a framework (React,
Vue) specifically to minimize setup time and avoid a build step,
given the hackathon time constraint and that only one page was
needed.

## Phase 8 — Deployment (Frontend + Backend CORS fix)

**Prompt (paraphrased):** Asked Claude to identify why the deployed
frontend couldn't reach the deployed backend, and to add CORS
support to the FastAPI app.

**Output used:** Added `CORSMiddleware` to `app/main.py` with
`allow_origins=["*"]`, appropriate for a hackathon demo where the
API has no authentication and isn't handling sensitive data.

**Deployment steps (human-executed, Claude-guided):**
- Backend deployed to Render (free tier), environment variable
  (`GROQ_API_KEY`) set via Render's dashboard, never committed to
  the repo.
- Frontend deployed to Netlify via drag-and-drop of the `frontend`
  folder, producing a public URL:
  `https://cheerful-torte-554076.netlify.app`

**Debugging (real, iterative):**
- Verified the CORS fix was actually live using `curl -i` with an
  explicit `Origin` header against the deployed Render URL, after an
  earlier Python `requests` test gave a misleading result (that test
  hadn't sent an `Origin` header, so it wasn't a valid CORS check).
- New Netlify site defaulted to "Private" visibility (a platform
  default introduced for accounts created after July 28, 2026),
  which presented a password prompt to visitors. Resolved via
  Project configuration → Visitor access → Project visibility → set
  to Public.
